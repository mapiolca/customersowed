# CustomersOwed 2.0.0 — correctif et validation

État du 2026-10-11 ; référentiel fourni `2026.09.09.2` ; base Git `8d3f577113e69aa83836d165d2e8e6196fafa4f0` ; branche `prepare-v2.0.0`. Version en préparation, aucune release ni déploiement effectué.

## Périmètre implémenté

Le rapport, le widget, les quatre modèles PDF et les envois manuels/planifiés utilisent les factures natives. Aucun nouvel objet métier persistant ni table de partage custom n'est ajouté. Les points d'entrée concernés sont la page du rapport, `fetch_lines()`, le widget, les modèles PDF, le téléchargement natif, les envois, le cron et l'administration.

- Droits : appels directs `hasRight()` ; restrictions commerciales maintenues avec un tiers explicite ; utilisateurs externes limités à leur tiers ; données de projet inaccessible masquées sans supprimer la facture autorisée. Les anciens droits 423100/423101/423102 sont migrés vers 42310001/42310002/42310003 pour utilisateurs et groupes, puis retirés pour éviter une réattribution lors d'une réactivation.
- Calcul : agrégats indépendants des paiements et avoirs, sans multiplication par les affectations commerciales ; prise en compte des avoirs consommés côté source et cible ; limite de date en fin de journée ; arrondis natifs `price2num(..., 'MT')`. Les états historiques exacts ne sont pas reconstruits : statut actuel des factures et date de création des remises restent des limites explicites.
- Multicompany : périmètres natifs facture/tiers ; colonne et filtre Environnement ; pagination SQL et totaux sur l'ensemble filtré. Le rapport agrégé appartient à l'entité courante ; ses PDF sont privés par utilisateur, avec manifeste des factures permettant de revérifier les accès au téléchargement. Les documents des factures utilisent leur entité propriétaire.
- Configuration : valeurs zéro et chaîne vide, modèles personnalisés et paramètres cron conservés ; migration du test cron historique ; conservation du libellé existant pour éviter un doublon après changement de langue.
- PDF : quatre modèles conservés ; réservation du pied natif mesuré sur une copie du PDF ; pieds intermédiaires puis pied final ; refus d'un pied trop volumineux. Rendu réel encore à valider.
- Interface : tokens natifs, contrôles serveur et redirection après les sauvegardes ; pagination dans le formulaire ; états vides et composants natifs ; onglets Compatibilité et À propos alimentés par le descripteur/la liste centrale.
- Cron : utilisateur d'exécution conservé, périmètre du destinataire intersecté avec celui de l'exécutant, verrou et marqueur quotidien par variante. Un envoi incertain reste bloqué plutôt que rejoué automatiquement. Aucun email réel envoyé pendant les tests.
- Nettoyage : API `MyObject` inutilisable et squelettes non employés retirés ; log serveur exclu ; aucune table ni donnée supprimée sur une instance.

La famille est exactement **Joliciel x Les Métiers du Bâtiment**, selon la demande explicite. L'ID historique **423100** est conservé : aucun nouvel ID 450000–450999 n'a été attribué et l'inventaire officiel/GitHub/parc privé n'a pas été confirmé. Un changement d'ID éventuel nécessite une décision et une migration distinctes avant publication.

L'envoi de ce rapport agrégé utilise `CMailFile` : il s'agit d'une diffusion volontaire ou planifiée, sans mutation CRUD d'un objet rapport. Les notifications natives sur événements CRUD ne couvrent pas cette opération. Aucun système parallèle d'abonnements n'est créé.

## Vérifications exécutées

Environnement local : PHP **8.2.11**, Python et SQLite isolé ; aucun core, SMTP, MySQL/MariaDB ou Multicompany actif.

- Sept tests Python exécutent les requêtes SQL émises par le code PHP sur des jeux de données isolés : paiements/avoirs multiples, restrictions commerciales avec tiers explicite, partage et projets, utilisateur externe, avoir consommé, pagination et totaux, migration des droits et conservation de configuration.
- Le harnais PHP vérifie également les refus de droits/entités/tri, l'absence d'état périmé, les chemins documentaires manquants ou erronés, la réservation du pied avec doubles de test, les téléchargements privés et la révocation d'accès, ainsi que la concurrence/reprise cron sans SMTP.
- Syntaxe des fichiers PHP du module vérifiée ; revue du diff complet et recherche des accès directs aux droits, wrappers natifs, arrondis financiers et chemins `/custom/` fonctionnels.
- PHPStan : non exécuté, outil et configuration absents du dépôt. Aucun baseline ni suppression d'erreur ajouté.

Ces tests sont des simulations et des contrôles syntaxiques ; ils ne constituent pas une preuve d'installation ni de fonctionnement sur une instance Dolibarr. SQLite ne valide pas le moteur MySQL/MariaDB de production.
